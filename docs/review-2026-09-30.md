# Is UniStudent a well-built AI plugin? An honest review (2026-09-30)

## Short answer

The design follows how good agent plugins are built today, and the size fits the job. It is not yet proven: it has never processed a real, whole course. That test matters more than anything else left.

## Size: is it too big?

| Part | Size | Loaded when |
|---|---|---|
| Python core (course folders, Wiki build, checks, recordings, MCP server) | ~2,100 lines, standard library only | Runs as commands; costs no AI tokens |
| Tests | ~1,100 lines, 70 tests | Development only |
| Skills + worker instructions | ~6,700 words across 10 skills and 5 workers | Only the skill being used (a few hundred to ~1,000 words) |
| Course context (`AGENTS.md` / `CLAUDE.md`) | ~570 words | Every conversation in a course folder |
| MCP tools | 24 tools, ~2,300 tokens of schema | Every conversation in an MCP app |

For comparison, `mcp-video-analyzer` exposes 8 tools for one job (videos). UniStudent does five jobs (course folders, Wiki, grounding, study packs, recordings), so 24 tools and 10 skills is proportionate. What a student has to know is small: **course-setup** once, then **course-add** and **study-pack**; **course-help** lists everything else.

## What's done the way experienced plugin authors do it

1. **Scripts do the mechanical work, the AI does the judgement.** Converting, hashing, linking, sorting and checking are deterministic Python; the AI writes explanations, study packs and summaries.
2. **Progressive disclosure.** Only short descriptions are always loaded; each skill's steps load when used; worker instructions and reference files load only when a step points at them.
3. **One source of truth.** The command line defines every operation; the MCP server's tools are generated from it; the grounding rule lives in one template.
4. **Checkable steps.** The procedural skills end each step with a "Done when" condition, most of them verifiable by a command (e.g. `wiki check` reports 0 problems). The economics skills are reference rules, not steps.
5. **Tests at the edges, plus a real-model eval.** Unit tests cover the three agreed seams; `evals/grounding` asks a real model six questions and grades the labels (6/6 on the last run).
6. **Portable, with one requirement.** An MCP server and open-standard skills, so it works beyond Claude; the one thing every student installs is `uv`, which runs the server with the right Python everywhere (Windows included). Skills installed on their own need the server (or the `unistudent` command) to do anything. It reuses established tools (MarkItDown, ffmpeg, faster-whisper/mlx-whisper with ivrit.ai Hebrew models, mcp-video-analyzer) instead of rebuilding them.
7. **Safe with the student's files.** One copy of every file (links instead of copies), study packs never overwritten, the student's own `CLAUDE.md`/`AGENTS.md` kept, and no course material in the repo.

## Weak spots, most important first

1. **Never run on a whole real course.** Everything is tested on small fixtures plus one real 184 KB download. Real courses bring scanned PDFs, Hebrew Word files with equations, 3-hour recordings, and odd file names. **Next step: run course-setup + openu-sync on the micro course end to end.**
2. **The site download is the most fragile part.** It drives the student's browser, and the recording links expire within hours. A site redesign breaks it; `site.md` has to be kept current.
3. **Token cost on a full course.** Building the Wiki's understanding layer and summarising ten 3-hour recordings is expensive. "Lite mode" is planned for v2; until then the recording steps always ask first.
4. **Hebrew speech-to-text is unverified on a real machine.** The model names are checked against Hugging Face, but speed and quality on a Mac haven't been measured.
5. **The grounding eval is small and in English.** Six English questions; it needs Hebrew cases from the real course.
6. **Not published yet.** No GitHub repo, so the `uvx` / `npx skills` / marketplace install lines are untested in practice (this sandbox can't reach PyPI, so `uvx` couldn't be tried here either). The package itself installs and runs from a local build, and a plain Claude client drove the MCP server successfully.
7. **The MCP server is hand-written** (standard library, tools and prompts only). It's tested, including bad input and failing tools, and a real Claude client used it, but it's less battle-tested than the official SDK (ADR 0004 says when to switch). Long jobs (transcription) run in the background so tool-call time limits don't cut them off.
8. **Windows hasn't been tried by a person.** CI is set up for it, but it runs only once the repo is on GitHub.

## Recommended order from here

1. Put the repo on GitHub (private is fine) so CI runs on all three systems and the install lines can be tried.
2. Run the micro course end to end in Claude Code on the Mac: setup → openu-sync → course-wiki → one study pack → one recording.
3. Fix what that run breaks; add 5–10 Hebrew eval questions from it.
4. Only then add v2 features (lite mode, exam plan, frames table of contents via mcp-video-analyzer).

## Fixed after a second, independent review (same day)

- The MCP server survived a failing tool, invalid JSON and unknown tools only partly: now every case returns a proper error and the server keeps running.
- Tools no longer show arguments that don't apply to them; required arguments are marked.
- The Claude plugin starts the server with `uvx` instead of `python3` (missing on many Windows machines).
- Worker instructions and the OpenU site notes are readable after a skills-only install (`us doc`, and the notes now sit inside the sync skill).
- Install hints for speech-to-text name the exact Python that runs UniStudent.

# UniStudent after v2 (tickets 01–06, 04): a from-scratch review (2026-09-30)

This is a second, independent pass, written fresh from the shipped code and skills (not from the design
conversation that produced them), for someone building their first AI plugin. It covers three things:
does the plugin actually make life easier for the student it's for, does it follow how experienced
plugin authors build agent tools, and does it use agentic concepts (grounding, layering, the
script-vs-judgment boundary, verification loops) correctly. Ticket 04 (token-friendly frame analysis) is
folded in here too, since it shipped in the same pass as 01/02/03/05/06.

**Shipped size right now:** 2,369 lines of Python (stdlib only), 1,328 lines of tests (92 tests, 11
skipped when optional tools aren't installed), 10 skills (~5,400 words total) plus 5 worker agents
(~1,330 words), and 32 MCP tools generated from the same command line the skills use. That's grown from
v1's 24 tools; still one job's worth of surface area per skill, and still nothing a student has to read
up front beyond `course-setup`.

## Does it serve the actual student? (goal-fit)

The stated goal: a non-technical student should be able to turn "whatever the course gave me" into a
Wiki the AI can be trusted to answer from, get study packs, find where a teacher flagged something in a
recording, and get answers restricted to the course material. Checked against that:

- **Getting started got measurably easier.** Before v2, a student with no installed university plugin
  hit a dead end ("downloading needs your university's plugin") and a student with no course skill
  silently got only generic rules with no course-specific emphasis, with no way to know that happened.
  Both dead ends are now interviews that produce something reusable (`course.py`'s
  `generated_university_file` / `generated_course_skill_file`), which is the right fix: it turns "we
  don't support you" into "tell us once."
- **Setup no longer punishes an interrupted session.** `setup-progress` (course.py's `SETUP_STAGES`,
  `write_setup_progress`/`read_setup_progress`) means a slow fetch-and-organize step doesn't cost the
  student a full re-interview if they close the laptop. `course-help` now surfaces this
  (`us setup-progress list`) instead of the student having to remember it happened.
- **The closing explanation earns its place.** `course-setup` step 6 now states, every time, the two
  things a non-technical student actually needs after setup (how to add material later, how to make a
  fresh AI session use this course's Wiki) — not buried in a README they may never open. This is the
  single highest-leverage change in this pass: it's cheap to skip and easy to forget, and it directly
  answers "so what do I do now?"
- **Gap: none of this has touched a real, whole course yet.** Every check above is true of the fixtures
  and unit tests; v1's review flagged "never run on a whole real course" as the top weak spot, and that
  is still true today — v2 adds new conversational branches (the university and course-skill interviews)
  that have *never been walked by a real student*, which is exactly the kind of thing unit tests can't
  catch (a confusing question, a bad default, a student typing something the interview didn't expect).

## AI-plugin best practices

1. **Scoping and naming are still consistent.** `university`/`course-skill`/`setup-progress` follow the
   existing verb-first, multi-action pattern (`prefs show|add`, `wiki build|check`) instead of inventing
   a new shape. Good — a student or another agent reading the tool list learns one pattern, not five.
2. **Context economy: mostly held, with one gap.** The generated fallback files never enter a course's
   Wiki or context file (`write_context_files` doesn't reference them) — correct, since they're
   university/subject-level advice, not course material, and loading them into every conversation would
   cost tokens for no benefit. The gap: nothing tells the *student* these files exist once written. A
   `~/.unistudent/generated/bar-ilan/site.md` a student wrote six months ago, for a course they've since
   dropped, has no visibility path (no `us generated list`, nothing in `course-help`) — it's a small
   amount of silent, unmanaged state. Not urgent, but it's the first crack in "every file this plugin
   writes, the student can see and understand."
3. **Deep-module design holds up.** `write_generated_reference()` (course.py) is a good example: one
   function, two very different callers (`university`, `course-skill`), no leaky parameters — the
   second call site made the first one's design honest instead of just copying it. That refactor
   happened *during* this pass, after the first code-review caught the duplication; worth naming
   because it's the kind of correction that's easy to skip under time pressure and wasn't skipped here.
4. **Portability is unchanged and still real.** The two new commands, like every other command, are
   plain argparse + JSON, so `unistudent-mcp` picks them up automatically for every MCP client, and
   `us <command> --json` still works with zero MCP server at all. No new client-specific assumption
   was introduced (checked directly: no `AskUserQuestion`, no "Skill tool" reference in the new skill
   text — `tests/test_skills.py::test_skills_name_no_client_specific_tools` covers this, and passes).
5. **Skill composability: one real risk introduced.** `course-setup` step 0 now instructs the agent to
   call `us setup-progress advance` after *every* numbered stage, including stages that live inside
   other skills it delegates to (step 4 fetch-and-organize hands off to `openu-sync` or a generated
   fallback's fetch instructions; step 5 hands off to `course-wiki`). Those two skills' own files were
   **not updated** to call `setup-progress advance` themselves — the progress bookkeeping is entirely
   `course-setup`'s responsibility, layered on top, never pushed down into the skills it delegates to.
   That's actually the right boundary (a delegated skill shouldn't need to know it's being resumed), but
   it means the resume mechanism is only as reliable as `course-setup` remembering to call it after
   *its own* delegation returns, not something structurally enforced. Worth a code comment or a "Done
   when" line making that division explicit, since it's not obvious from reading `openu-sync/SKILL.md`
   alone that it has no resume awareness at all.

## Agentic concepts, used correctly?

- **Grounding labels: untouched, correctly.** Nothing in this pass touches `wiki.py`'s `check()` function
  or `labels.py`'s ✅/💡/⚠️/❌ scheme, and it shouldn't have — grounding is about course material, and
  every v2 change lives on the university/setup/recording axis, not the material axis. Confirmed by
  re-reading (`test_grounding_labels.py`: unaffected, still passing).
- **Generic-vs-specific layering: extended correctly, with one asymmetry worth naming.** The
  university axis now has three tiers (installed plugin → generated fallback → interview), and the
  study-pack/course-skill axis got the same three tiers applied on top of the *existing* two-tier
  layering (field skill → course skill). But the two axes' "generated" tier are structured differently:
  a generated university fallback is a flat reference file with no further specialization point, while
  a generated course-skill fallback sits *underneath* the same layering rule as a real course skill
  ("later wins" in study-pack step 3) — meaning a generated fallback and student preferences can
  conflict, and preferences correctly win, but a generated fallback and a *real* field skill installed
  later have no defined precedence (what happens if `economics` gets installed after a generated
  biology-shaped fallback already exists for an economics course?). ADR 0005 says the cache "behaves
  identically to a hand-authored plugin from then on," which implicitly means: forever, even after a
  real plugin exists. That's a defensible choice (once-generated, stays authoritative until the student
  asks to redo it) but it is not currently written down anywhere a future reader would find it, and it's
  the kind of thing that will confuse someone in six months.
- **Deterministic-script vs. agent-judgment boundary: held correctly.** Every new capability follows the
  existing split: `us university save` / `us course-skill save` / `us setup-progress advance` are pure,
  deterministic writes (no judgment, no LLM call inside them); the *interview itself* — deciding what to
  ask, when the student's answer is good enough to save — stays entirely in skill prose, exactly where
  judgment belongs. Same for frame analysis (ticket 04): `recordings.estimate()`'s segment count is a
  deterministic arithmetic fact; *whether* to spend the tokens is the one place a human decision was
  correctly kept out of code and given its own explicit yes/no.
- **Verification/self-checking loops: not extended, and that's a genuine gap, not a neutral one.** The
  existing loop (`wiki check` → fix → `wiki check` again; the `verifier` worker's "run it again" step) is
  code-checkable because course material has ground truth to check against. The two new interviews have
  no equivalent: `course-setup` step 1 says "show back what you're about to save" before writing a
  generated university fallback, which is a confirmation, not a verification — there is no step that
  later re-checks whether a generated fallback actually worked (did the site-URL-based fetch instructions
  the student described actually let a later session download anything?). For a plugin whose whole pitch
  is "grounded, checked, not guessed," a once-confirmed-never-re-verified fallback is the one place in
  this pass where "the AI wrote something down and everyone just trusts it from now on" — worth being
  honest about, even though the alternative (re-verifying a student's own free-text description) isn't
  obviously better.

## Prioritized findings

1. **(Ship-blocking for confidence, not for correctness) Nothing in this pass has been run against a
   real course or a real student.** Same conclusion as the v1 review, now with more surface area at
   risk: two brand-new conversational branches (university interview, course-skill interview) that have
   never been walked once outside a unit test's canned CLI calls.
2. **Ticket 04's code hasn't reached CI yet.** `git log` shows the local `main` is one commit ahead of
   `origin/main` at review time (`b7f4b7b` vs `d3b8b78`) — ticket 04 (frame-analysis opt-in) has run the
   full local suite but not the GitHub Actions matrix (3 OSes × 2 Python versions × 2 dependency sets).
   Cheap to fix: push, watch it go green.
3. **The generated-fallback vs. real-plugin precedence rule is a real decision with no written answer.**
   Once economics (or any field) ships a plugin, does an existing generated fallback for that field keep
   winning, or does the real plugin take over automatically? Pick one and write it into ADR 0005 or a new
   ADR before it comes up in practice, not after.
4. **No visibility into what's been generated.** A `us generated list` (mirroring `setup-progress list`)
   costs little and closes the "silent unmanaged state" gap named above.
5. **`course-setup`'s resume bookkeeping is a single point of failure by design, and that design choice
   isn't documented anywhere.** Not asking to change it (pushing resume-awareness into every delegated
   skill would be worse) — asking that the SKILL.md say so explicitly, so the next person touching
   `openu-sync` or `course-wiki` doesn't assume it participates in resume and doesn't need to.

## Follow-up tickets this review surfaces

- **08: Document generated-fallback precedence over a later-installed real plugin** (extends ADR 0005;
  no code change if the answer is "generated fallback keeps winning until the student redoes it," a
  small `course-skill`/`university` check if the answer is "a real plugin should take over").
- **09: `us generated list`** — a status command mirroring `setup-progress list`, so `course-help` (or a
  student directly) can see what's been generated and when, closing the visibility gap in finding 4.
- **10: Run `course-setup` end-to-end against a real course** (the same recommendation the v1 review
  made and that still hasn't happened) — now specifically exercising both new interview branches
  (no installed university plugin, no installed course skill) with a real student, not fixtures.

None of these are blocking; they're ordered by how cheap they are to leave undone, cheapest-to-defer
last.

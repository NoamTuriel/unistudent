# Spec: UniStudent plugins (v1: Open University + economics)

> Layout sections superseded by ADR 0007 (three visible folders, hidden Wiki, no Raw).

Status: in grilling · Created 2026-09-29 · Updated 2026-09-30 (grilling rounds 1–2; decisions after first build; portability) · Owner: Noam
Vocabulary: see `CONTEXT.md` (Course folder, Raw, Wiki, Study pack, Grounding label, Origin, …).

## Problem Statement

Open University students get their course material scattered across the course website (Moodle / "אופל"): lecturer slides, "questions with answers", assignments with solutions, past exams, formula and assumption sheets, and many hours of session recordings. Turning this into something they can study from is slow manual work: downloading everything, sorting it by unit, watching hours of video to find where a topic is explained, and writing summaries.

When they ask a general AI for help, the answers are drawn from the whole internet. They often use models, methods, notation or material from other courses or more advanced levels. An answer can be correct in general and still wrong for this course's exam, because the exam grades the course's own methods, assumptions and notation. Students can't easily tell which parts of an AI answer belong to their course.

Students also rarely know how to set up Claude with skills, context files and a knowledge base, so they can't get the benefit of a course-aware assistant on their own.

## Solution

A family of installable Claude plugins in one repo (one marketplace). The student installs three layers once:

- **UniStudent core** (university-agnostic): course folders, Wiki, recordings, study packs, grounding labels, help.
- **A university plugin** (v1: Open University): everything specific to that university — site access, site structure, sorting by its units, its exam conventions.
- **Subject plugins** (v1: economics, with the macro course skill): how to build study packs for a field or course. Independent of the university.

Together, for an Open University student, they:

1. Onboards the student with a few questions per course: which course, where and in what format to save, and whether to download from the site, import their own folder, or both.
2. Downloads the course material from the OpenU website and sorts it locally by unit, in a human-readable layout. Recordings are optional, and the student is asked first.
3. Builds a separate **LLM wiki per course**: Markdown versions of every source, recording transcripts with timestamped tables of contents and summaries, a glossary, a question bank and a unit index. This gives the AI an indexed, course-only knowledge base.
4. Writes a short course context file (exam format, exam date, units, formula sheet, lecturer emphasis) that points into the wiki. Any session opened in that course folder then "knows the course".
5. Offers a menu of actions afterwards: unit study packs (the student picks which pages, all by default), syncing new material, adding material from an inbox, recording summaries, and exam prep.
6. **Grounds every answer in the course wiki.** It labels what comes from course material, what doesn't, and what conflicts with it.
7. Explains itself to the student, in chat and in a README inside the course folder, so they understand the flow and keep feeding it material.

Study-pack rules come in layers: generic rules (core) → field skill (e.g. economics) → course skill (e.g. macro) → student preferences. If the student's course has no course skill, the generic rules are used. When the student asks to change how material is handled or how study packs look, the change is saved to the student preferences for that course, applied to every unit from then on.

## User Stories

### Install and onboarding
1. As a student, I want to install the plugin once, so that it works for all my courses without reinstalling.
2. As a student, I want a single setup command that walks me through everything, so that I don't need to know how Claude skills work.
3. As a student, I want to pick my course by name from a list of the installed course skills (names are the same across universities), so that I get the best summary format for it.
4. As a student whose course isn't in the list, I want the plugin to still work with a generic template, so that I'm not blocked.
5. As a student, when I ask for a change that affects a whole unit's study pack (not just one paragraph or explanation), I want to be asked "only this unit, always for this course, or for all my courses?", and the answer saved to the matching preferences file, so that I say it once. Small edits to one paragraph are just done, without asking.
6. As a student, I want to choose where my course files are saved (any local folder, including a Google Drive or iCloud synced folder), so that the output lives where I already keep my files.
7. As a student, I want to choose between Obsidian-style Markdown and plain Markdown, so that links and callouts render correctly in the app I use.
8. As a student, I want to choose whether the plugin downloads material from the OpenU site, imports a folder I already have, or both, so that nothing I've collected is lost.
9. As a student, I want the plugin to ask only for the folder access and login it actually needs, so that I feel safe using it.
10. As a student, I want my answers saved per course, so that I'm not asked the same questions again.
11. As a student, I want to run setup again for another course, so that I can add courses at any time.

### Multiple courses
12. As a student taking several courses, I want each course in its own folder with its own wiki, inbox and settings, so that courses never mix.
13. As a student, I want the plugin to detect which course I'm in from the folder or project I opened, and tell me ("working on: Macro"), so that I always know which course it's using.
14. As a student, I want the plugin to use the course my request is clearly about, and to ask only when that's unclear, so that it neither guesses wrong nor asks needlessly.
15. As a student, I want to list and switch between my courses with one command, so that I don't have to remember paths.
16. As a Cowork user, I want one project per course with that course's folder connected, so that everything in the project is scoped to that course.
17. As a Claude Code user, I want to open Claude in a course folder and have everything scoped to it, so that the setup is the same idea in both apps.

### Download and sorting
18. As a student, I want all the material on my course website downloaded (slides, Q&A files, assignments and solutions, past exams, exam aids), so that I have everything locally.
19. As a student, I want downloaded files sorted by unit in a human-readable folder layout, so that I can find things myself too.
20. As a student, I want an exact mirror of the original files kept untouched, so that I can always go back to the source.
20a. As a student, I want every file stored only once on disk, with the human-readable layout made of links to it, so that large recordings don't take double the space.
20b. As a student importing my own folder, I want my files used where they are instead of copied, so that nothing is duplicated.
20c. As a student, I want files the plugin can't place in a unit collected in one "unsorted" place and asked about in one grouped question at the end of a sync, with my answers remembered, so that sorting is right without constant questions.
21. As a student, I want each file's origin recorded (website section, or my own folder), so that I know where everything came from.
22. As a student, I want downloads to resume after an interruption, so that a dropped connection doesn't mean starting over.
23. As a student, I want a sync command that downloads only what's new since last time and tells me what changed, so that I can keep up weekly.
24. As a student, I want the plugin to use Claude in Chrome with my logged-in session for now, so that I don't have to hand over my password.
25. As a student, I want the download method to be replaceable later by a direct login or API, without changing anything else I use, so that the plugin can get faster without re-learning.

### Videos and recordings (always opt-in)
26. As a student, I want to be asked whether to include recordings before any download, with a note that it's recommended but slow, so that I stay in control of time and disk space.
27. As a student, I want to see real estimates first (number of recordings, total hours, GB, estimated download time), so that I can decide knowingly.
28. As a student, I want to choose a processing level per course (skip / download only / table of contents from video frames / full transcript and summary), so that I can match my computer's power and my token budget.
29. As a student, I want a clear warning that transcription and video analysis are heavy and slow, with an estimate for my machine, before it starts, so that I'm not surprised.
30. As a student, I want to process only the recordings for the unit I'm studying now, so that I get value quickly without processing the whole semester.
30a. As a student whose course folder is in iCloud or Google Drive, I want recordings kept in one local folder that doesn't sync, with pages linking to them, so that links don't break and large files aren't pushed to the cloud.
31. As a student, I want my video choices remembered per course, so that I'm not asked every time, while still being able to change them.
32. As a student, I want Hebrew transcription that handles lecture audio well, so that the transcripts are usable.
33. As a student, I want each processed recording to have a timestamped table of contents (explanation / example / practice / exam question / announcements), so that I can jump to the moment a topic is taught.
34. As a student, I want a summary of each recording, including important announcements and "this is always on the exam" moments, so that I don't miss what the lecturer stressed.

### LLM wiki
35. As a student, I want every PDF, Word and slide file converted to Markdown (with formulas preserved), so that the AI can read and index them.
36. As a student, I want a wiki index listing units, sources and recordings, so that the AI (and I) can navigate quickly.
37. As a student, I want a glossary of the course's terms and notation as the course uses them, so that answers use my course's symbols.
38. As a student, I want a question bank with every question from Q&A files, assignments and past exams, tagged by unit and topic, with a link to where it's solved in a recording if it is, so that I can practice by topic.
39. As a student, I want each unit's page in the wiki to record the approved methods, notation and assumptions for that unit, so that the AI knows what counts as a valid solution in my course.
40. As a student, I want the wiki to be rebuildable from the raw files at any time, so that improvements to the plugin can be applied to existing courses.
41. As a student, I want links from the wiki and my study pages back to the original file and the exact recording timestamp, so that I can check the source.

### Course context
42. As a student, I want a short course context file created automatically (exam format, exam date, units, formula sheet location, lecturer emphasis), so that every new session already knows my course.
43. As a student, I want that context file kept short and pointing into the wiki, so that it doesn't burn tokens every session.
44. As a student, I want the plugin to learn how the exam works from the exam-info files and past exams, so that its advice matches the real exam.

### Grounding in course material
45. As a student, I want every answer to label what comes from my course material (✅ with a link to the source), so that I can trust it for the exam.
45a. As a student, I want Claude's own explanations of my course material (examples, analogies, memory tricks) marked 💡 with a link to what they explain, rather than ⚠️, so that helpful explanations aren't treated as outside the course.
46. As a student, I want to be told clearly when part of an answer is not in my course material (⚠️), so that I don't study something the course doesn't teach.
47. As a student, I want to be told when a general method or fact conflicts with how my course does it (❌), with the course version given first and the difference explained, so that I answer the exam the way it's graded.
48. As a student, I want to be told when the wiki simply doesn't cover my question, with a suggestion to add a source to the inbox, so that gaps get filled instead of guessed.
49. As a student taking several courses, I want material from my other courses flagged as "from your other course, not this one", so that I don't mix courses on the exam.
49a. As a student, I want one grounding label per paragraph (not per sentence), so that answers stay readable while every part is still marked.
50. As a student, I want to be able to explicitly ask for outside knowledge or a comparison between courses, and have it clearly labeled, so that I can still explore when I choose to.

### Unit study packs
51. As a student, I want to see all the pages a unit pack can include and what each gives me, and pick which to create (all selected by default), so that I get only what I need.
52. As a student, I want the default pages to be a roadmap (what to memorize vs understand), a topic-by-topic walkthrough, practice ordered by topic, and a recordings table of contents, so that I can follow a proven study flow.
53. As a student, I want each unit split into a small set of topics that every page shares, so that the pages line up with each other.
54. As a student, I want every claim in a unit pack to link to its source, so that the grounding rule applies to summaries too.
55. As an economics student, I want explanations in the economics style (plain words, simple explanation, deep explanation, formula, memory trick), so that concepts are easy and exam-ready.
56. As a macro student, I want macro-specific pages and exam patterns (e.g. the recurring question types and the course's solution tools), so that my pack matches how macro is tested.
57. As a student, I want my study pack edits kept safe: when new material arrives, I want the plugin to propose changes ("2 new questions for topic 3, add them?") and apply them only after I agree, so that my work is never overwritten.
58. As a student, I want a verifier to check the pack (links resolve, timestamps exist, no unsourced claims) before it's handed to me, so that I can trust it.

### Adding more material
59. As a student, I want an inbox folder where I can drop anything (a friend's summary, an exam PDF, a photo of notes), so that feeding the plugin is effortless.
60. As a student, I want one command that sorts inbox files into raw, updates the wiki and the right unit, and tells me what it did, so that new material is used right away.
61. As a student, I want material I add to be labeled by origin (e.g. "friend's summary" vs "lecturer"), so that answers can say how official a source is.
61a. As a student, I want official material (course site, or files I mark as the lecturer's) to win over added material when they conflict, so that the exam version is always first.

### Exam prep (v2)
62. As a student, I want a study plan built backwards from my exam date and the units left, so that I know what to do each day.
63. As a student, I want past-exam questions grouped by topic, so that I can find my weak spots before the exam.

### Platforms
63a. As a student on macOS, Windows or Linux, I want every feature to work on my machine, so that the plugin isn't Mac-only.

### Guidance and cost
64. As a student, I want the plugin to explain how it works (raw → wiki → study, the inbox, grounding labels) at setup and whenever I ask for help, so that I use it correctly.
65. As a student, I want a README in my course folder explaining the same, so that I can read it without asking.
66. As a student, I want to be asked before any heavy step, with an estimate, so that I control time and token use.
67. (v2) As a student with a limited plan, I want a lite mode that skips optional heavy steps, so that I can still use the core features.

### Maintainer
68. As the maintainer, I want the repo to ship code and skills only, never course material, so that nothing copyrighted is redistributed.
69. As the maintainer, I want field and course skills to be small add-ons that only add or override rules on top of the generic rules, so that adding a new course is cheap.
69b. As a student at any university, I want the core to work without a university plugin (importing my own folder and the inbox only), so that I get value even before my university is supported.
69a. As the maintainer, I want university-specific code isolated in one university plugin, so that another university can be added without touching the core or the subject plugins.
70. As the maintainer, I want the plugin tested against saved copies of OpenU pages, so that site changes are caught.

## Implementation Decisions

### Packaging
- **Portable (ADR 0004):** the core ships as a Python package with a command line (`unistudent`) and an MCP server (`unistudent-mcp`, tools generated from the command line, skills also served as prompts), installable with `uvx` from the Git repo. Skills use the open Agent Skills format with collision-safe names, so they install into any agent with `npx skills add`. The course context is written to `AGENTS.md` and imported by `CLAUDE.md`. Existing tools are used where they exist: MarkItDown, ffmpeg, faster-whisper / mlx-whisper with ivrit.ai models, mcp-video-analyzer.
- One Git repo acting as a Claude plugin marketplace ("UniStudent"). Works in Claude Code and Cowork.
- Plugins in v1:
  - **`unistudent`** (core, university-agnostic): onboarding, course folders and course detection, Raw/Manifest, inbox, recordings pipeline, Wiki building, course context file, grounding rule, study-pack skeleton and page picker, student preferences, help.
  - **`openu`** (university plugin): the fetcher for the OpenU site, site structure knowledge, sorting files into OpenU units, OpenU exam conventions. It plugs into core through the fetcher and sorting interfaces.
  - **`economics`** (subject plugin): the economics field skill and the macro course skill.
- Subject plugins never depend on a university plugin, and university plugins never contain study-pack rules.
- The core works on its own (import from the student's folder and the inbox). A university plugin adds downloading from the site.
- A course is matched to a course skill by course name, which the student picks from the list of installed course skills.
- The repo contains skills, subagents, slash commands and scripts, and no course material. Only the maintainer publishes to the repo.

### Rule layers for study packs
- Order (later overrides earlier): **generic rules** (core) → **field skill** → **course skill** → **general preferences** → **course preferences**.
- **Field skill** (first: economics): how to explain concepts in that field, and field-wide page content rules.
- **Course skill** (first: macro, derived from the existing `macro-unit-summary` skill): which study-pack pages exist and what's in them, exam question patterns, the course's recurring solution tools. Contains only what stays true across semesters. Per-semester and per-student facts (lecturer, recording-to-unit mapping, exam date) go in Settings.
- **Student preferences:** two files, never a skill. **Course preferences** live in the course folder; **general preferences** live next to the Registry and apply to all the student's courses. Course preferences win when they conflict. Skills (course, field, core) are never modified by what a student asks; only these files are. Written when the student asks for a change that affects a whole unit's study pack or how material is handled, and answers the one confirming question ("only this unit, always for this course, or for all my courses?") with one of the last two. Changes to a single paragraph or explanation are one-off edits and are never saved as rules. Read by the core before every study-pack build, so they work the same in Cowork and Claude Code (Cowork doesn't load skills from a connected folder). Applied to all units from then on. Never published.

### Per-course folder (the student's side)
- One folder per course, fully self-contained:
  - `raw/`: an untouched mirror plus a manifest of every file, with its origin, hash and download state.
  - `wiki/`: derived, AI-oriented Markdown.
  - `study/`: human-facing unit packs.
  - `inbox/`: the drop zone.
  - A short course context file (read at session start).
  - A README for the student.
  - A hidden settings file.
- **Settings** (per course, local only): course skill used, storage location and format flavor, source mode, video level, exam date, recording-to-unit mapping, lite-mode flag.
- **One copy of every file.** Raw holds the only real copy. The human-readable, by-unit layout is made of links into Raw (symlinks on macOS/Linux; on Windows, hard links for files and junctions for folders, which need no admin rights; if links can't be made, an index page with file links). Files imported from the student's own folder stay where they are: the Manifest records their path and Raw links to them. Recordings are never copied.
- **Sorting:** a file is assigned to a unit only on clear evidence (file name, site section, a unit title on its first page). Everything else goes to an unsorted area and is asked about in one grouped question at the end of the sync. Answers are stored so they're never asked twice.
- **Synced folders:** if the course folder is inside iCloud, Google Drive or another synced folder, setup explains the issue once and keeps recordings in a local, non-synced folder; pages and the Wiki stay in the synced folder and link to the recordings. (Synced folders don't carry links reliably, and iCloud may evict large files to the cloud.)
- **Ownership:** the plugin owns Raw and the Wiki and may rewrite them at any time. Study packs belong to the student once created. Updates to them are proposed as a change list and applied only after the student agrees.
- **Language:** every folder name is English (including unit folders: `Unit 4`, `General`, `Unsorted`). Page titles and content are in the course's language (Hebrew for OpenU). Skills are in English.
- **Registry** in the user's home folder listing all the student's courses and their paths, for listing and switching.
- **Course detection:** every command first looks for the settings file in the current folder or project. It announces the course, or asks if it's missing or ambiguous.

### Onboarding order
1. Course: pick from the course skills in the repo, or "not listed".
2. Storage location and format (Obsidian or plain Markdown). Request only the needed folder access.
3. Source: download from the site, import my folder, or both.
4. Videos: include or not, then the processing level, each with estimates. Heavy steps are always a separate, explicit question.

Answers are saved to settings. Setup ends by explaining how the plugin works, then offering the action menu.

### Fetching
- A **fetcher interface** separates "list what's on the course site and get each file" from everything else.
- The fetcher belongs to the university plugin. The v1 OpenU fetcher uses Claude in Chrome with the student's logged-in session to read course pages and collect file entries and URLs. A script then downloads the files using that session where possible. Browser-driven saving is a fallback.
- Later fetchers (Moodle mobile-app token, cookie reuse, headless login) plug into the same interface. Credentials, if ever used, go in the OS keychain and never in files.
- Sync is manifest-driven and idempotent. It resumes after interruption and reports what's new since the last sync.

### Video pipeline
- Processing levels:
  0. Skip
  1. Download only
  2. Table of contents from video frames (keyframes + OCR, no speech-to-text)
  3. Full transcript + table of contents + summary
- Before asking, the plugin computes estimates (count, hours, size, time on this machine).
- Processing can be limited to one unit's recordings.
- Hebrew speech-to-text uses a Hebrew-tuned Whisper model, running locally, on every OS. The backend is picked per machine (Apple-silicon-optimised on Macs, a CPU/GPU backend elsewhere) behind one interface, and the time estimate comes from a short benchmark on first use.
- Recording table-of-contents row types: explanation, example, practice, exam question, review, announcements, lecturer to camera.

### Wiki contents
- An index.
- Per-source Markdown conversions (Word files go to PDF before text extraction, so formulas survive).
- Per-recording transcript, table of contents and summary.
- A glossary (course notation).
- A question bank (unit, topic tag, source, solved-in-recording timestamp).
- Per-unit pages including approved methods, notation and assumptions.
- Every wiki page records its sources.

### Grounding rule
- Applies to chat answers and to generated pages.
- Labels:
  - ✅ from course material, with a link.
  - 💡 Claude's own explanation of course material (wording, example, analogy, memory trick), adding no fact, method or notation the Wiki lacks, with a link to what it explains.
  - ⚠️ not in course material. Material from another of the student's courses is labeled as such.
  - ❌ conflicts with the course. The course version comes first.
- Two tiers of course material: **official** (from the course site, or files the student marks as the lecturer's) and **added** (everything else the student brings, e.g. a friend's summary). Added material is labeled with its origin. When the two conflict, official wins.
- A "not covered" answer suggests adding a source to the inbox.
- Granularity: one grounding label per paragraph of an answer or page. A paragraph built only from course material carries ✅ with its sources.
- Outside knowledge is allowed only when the student asks, and it's always labeled.
- Enforcement is by instructions plus a verifier. This is not a hard guarantee, so the labels are what make slips visible.

### Scripts and platforms
- All scripts are Python, one codebase for macOS, Windows and Linux. No shell scripts, no per-OS script folders.
- The few OS-specific behaviours (making links, the credential store, the transcription backend, opening files) sit behind small internal adapters in that Python code, so every command behaves the same everywhere.
- External tools (e.g. ffmpeg) are checked on first use, with install guidance for the student's OS.

### Subagents
Subagents run behind commands and are never shown to the student as a menu:
- **Recording processor:** one per recording, in parallel. It returns only the summary to the main conversation.
- **Source converter:** batches of documents.
- **Unit-pack writer:** one per unit.
- **Verifier:** links, timestamps, unsourced claims.

Anything deterministic (downloading, converting, transcribing, link-building) is a script, not an agent.

### Student-facing commands (v1)
- Setup (new course)
- Courses (list/switch)
- Sync
- Add (process inbox)
- Wiki (build/refresh)
- Recordings (process, by unit)
- Unit (build a study pack with the page picker)
- Help
- (v2) Exam plan

### Unit pack
- A shared topic list per unit (4–6 topics, each with a tag) is the backbone of every page.
- Default pages from the generic skeleton: roadmap, walkthrough, practice by topic, recordings table of contents. Field and course skills can add, remove or reshape pages.
- The page picker shows each available page with a one-line "what it gives you", all selected by default.

## Testing Decisions

- **Good tests check external behavior only:** given inputs at a seam, is the output correct? They don't check how it was produced.
- **Seam 1, sync:** saved copies of OpenU course pages (HTML fixtures) plus fake file responses → expected `raw/` tree, manifest contents, unit sorting, a resume after simulated interruption, and a second sync reporting only new files. The existing open-source `openu-video-downloader` repo keeps HTML fixtures of OpenU pages the same way, which is prior art for this style.
- **Seam 2, wiki build:** a small fake course folder (a few PDFs and Word files, one short recording or a stub transcript) → the expected set of wiki pages: index, per-source Markdown, glossary entries, question bank entries with tags and sources, and unit pages.
- **Seam 3, grounding eval:** a fixed set of questions against a fixture wiki, each with its expected label (✅/⚠️/❌/not covered) and required citation → check the labels and that the citations point to real wiki pages. This includes cross-course cases (a question answered by the "other course" fixture).
- Run seams 1–2 on every change. Run seam 3 as a periodic eval, since it involves the model.

## Out of Scope (v1)

- Direct API or headless login. v1 uses Claude in Chrome; the fetcher interface keeps the door open.
- Universities other than the Open University (the university-plugin layer keeps the door open).
- Exam plan, past exams by topic, table of contents from video frames (video level 2), lite mode. These are v2.
- Publishing student preferences back to the repo.
- Google Drive API, Notion or other non-folder storage. Synced folders cover Drive and iCloud.
- Sharing wikis between students.
- Any redistribution of course material.
- Field and course skills beyond economics and macro.

## Further Notes

- The existing `macro-unit-summary` skill and its helper scripts are the reference implementation for the unit pack and the recordings table of contents. Its per-semester facts (recording mapping, paths, lecturer) move into local settings when it becomes the macro course skill.
- Prior art worth studying for fetching: Moodle-DL (Moodle mobile-app token with single sign-on), `openu-video-downloader`, and an OpenU video-downloader Chrome extension.
- Transcription speed depends heavily on the student's machine. The estimates shown before heavy steps should be based on a quick benchmark on first use.
- Generalizing the macro workflow should not touch the maintainer's live macro study files until after his 2026-10-06 exam.

# Spec: UniStudent v3 — one generic study-pack engine, pictures that follow the course, no subject layer

Status: grilled with the owner, ready to ticket · Created 2026-10-06 · Owner: Noam · Addendum 2026-10-13: setup you can walk away from (end of this doc, tickets 34 to 37)
Extends `docs/spec/v1.md` and `docs/spec/v2.md`: read those first. This doc covers only what changes. Decisions here supersede ticket 02 (generated course rules), ticket 23 (picture tools offer) and the subject half of ADR 0001; the ADRs that record the new decisions are listed under Implementation Decisions.

Vocabulary is `CONTEXT.md`'s. Terms this spec retires: Course skill, Field skill, Subject plugin, Picture kind, Tool offer. Terms it adds: Presentation, Known gaps, Recommended tool, Tool list.

## Problem Statement

A real study-pack run (one unit, one course, 2026-10-03) and a second unit built after it showed where the plugin is weak, and the owner's own position as the only maintainer showed where its design cannot scale.

1. **The subject layer cannot be maintained honestly.** Study-pack rules live in four layers (generic, field skill, course skill, preferences). The field and course skills exist for one field. Writing one per major means writing rules for courses the maintainer has never taken and cannot test on a student; not writing them means every other major gets the generic rules anyway. Measured against the generic rules after their tuning, the two existing skills add about ten lines that are truly field-specific; the rest is either already generic or generic advice phrased with one field's examples. The generated per-course rules (ticket 02) ask the student what to emphasise before the student has learned the material, which they cannot answer.
2. **Pictures do not look like the course, and the tool offer never fired.** The plugin offers drawing tools before the first Study pack by scanning the Wiki for English keywords; on the only real course (a Hebrew Wiki) it offered nothing. The three picture kinds beyond graphs were never checked against a course. Meanwhile the one kind that mattered, graphs, installed itself silently on first use, which dissolved the offer's premise. The feature was built, then reverted on a branch that was never merged, so the repo ships a dispatcher and an offer nobody uses.
3. **The packs read as prose where the course teaches in tables, steps and arrows.** A unit whose slides present a ledger on every page produced a walkthrough with zero tables. Two causes: the PDF converter keeps spacing but no table structure, so the Wiki never had the table; and the concept menu prescribes five prose fields per concept and no rule says "present it in the form the course uses".
4. **The build stops to ask, cannot resume, and its workers cannot use the tools.** The writer and verifier workers are ordered to run `us check` and `us graph` but their tool allowlist has no UniStudent tool, so verification became a separate step and one pack told the student to install a library by hand. A partial pack is reported as "no pack", so a resumed build starts over or asks which pages to build. Rules are pasted in full into the worker's prompt (about 25 KB). The check output for one unit is about 98 K characters. Every `file:` link is about 300 characters and repeated per line. `coverage.md` reports analysed sources as pending. The question bank's "solved in a recording" field is written before any recording exists and stays "no" forever. Short-version grouping was decided from question descriptions, not solutions. "Say it" quotes are never checked against the source. Drawn graphs are compared with the slide only by the writer that drew them.
5. **The plugin only works for a university student.** Setup's first question is "which university" with no "none" answer, so a self-learner with a folder of material has no way in, although the Core never depends on a University plugin.

## Solution

One generic study-pack engine that defers to the course material for everything field-specific, in six steps, each its own ticket (order at the end):

1. **Back to graphs only.** Merge the revert of the picture-tool offer: no dispatcher, no untested kinds, no offer, no evidence scan. `us graph` and Mermaid flowcharts stay. The roadmap's closing line names what the plugin draws and gives one example request the student can type in chat.
2. **No subject layer.** Delete the field and course skills, the `course_skill` setting, the generated course rules and the subject plugin recommendation. The ten field-specific lines become conditional advice in the generic rules. Emphasis comes from the Wiki's course page (exam format, lecturer emphasis, past-exam patterns), corrections from Course preferences and General preferences. Two plugin layers remain: Core and University plugin.
3. **Form follows the course.** A concept is presented in the form its source uses (a ledger as a table, a procedure as numbered steps, a comparison as a table, a cause chain as a flowchart, a curve as a Graph), and the concept menu becomes a coverage checklist, not a paragraph sequence. The Wiki unit writer records, per topic, the Presentation the course uses and the slide it is on, so the pack writer opens that slide and copies the form, and so the plugin knows which pictures the course shows.
4. **An unattended, resumable, tool-equipped build.** Workers get the UniStudent tools. No run stops to ask a question. Resume builds the missing pages and rebuilds only what the request named. Workers get rule file paths, not pasted rules. Links are written once per recording per section. Three new `us check` problem kinds make the rules mechanically checkable where they can be: notation and assumptions against the unit page, quoted "Say it" lines against the source text, and the shape of the writer's return. The verifier compares every drawn Graph with its slide. The two `coverage.md` bugs are fixed, the solved-in-a-recording field is written only when it is knowable, and the Short version is grouped from solutions, always.
5. **Recommended tools, on paper first.** A hardcoded Tool list, each entry proven by one sample call in CI, is the only source of recommendations. Python libraries become self-installing kinds; everything else is written into the course folder's MCP config or named with steps, per harness. An entry joins only when a real course shows a picture nothing draws. The roadmap line, not a question, tells the student what to ask for; the install happens in chat on request. The flow's code lands with the first entry.
6. **Self-study.** Setup's university step accepts "none", which skips plugin recommendation and the site interview, and the Core's wording that assumes a lecturer or an exam becomes conditional where that is cheap.

## User Stories

### Subject layer

1. As a student in any major, I want a good Study pack from the generic rules alone, so that my major does not need a hand-written skill before the plugin works for me.
2. As a student, I want the pack's emphasis to come from my course's own exam information and past exams, so that I am not asked what matters before I have learned it.
3. As a student, I want my corrections ("fewer graphs", "always a symbols table") saved as course or general preferences, so that the next unit follows them without my repeating them.
4. As a student in an economics course, I want the advice that was in the economics skill (models and shifts, assumptions sheets, formula sheets) to still apply when my course has those things, so that deleting the skill costs me nothing.
5. As a student who installed the economics plugin earlier, I want the plugin to keep working with it present and to be told once that it can be uninstalled, so that nothing breaks and nothing nags.
6. As the maintainer, I want exactly two plugin layers, Core and University, so that adding a major is never my job.
7. As the maintainer, I want the per-course layer to be the preferences file the student can read and edit, and nothing else, so that there is one place a course's rules live.

### Pictures

8. As a student, I want the graphs in my pack drawn with my course's own labels and shapes, so that I can compare them with my slides and trust them.
9. As a student, I want every picture my course shows that the plugin cannot draw to be a link to the slide and one line in words, so that nothing is silently missing.
10. As a student, I want the roadmap to tell me, in one line, what the plugin can draw and one example of what I can ask for in chat, so that I learn the plugin can illustrate on demand.
11. As a student, I want the roadmap to tell me, per kind of picture my unit shows that the plugin cannot draw, what to say in chat to add the tool, so that I am never asked during a build and never left without a way to get it.
12. As a student, I want to say "add the circuit tool" in chat and have the plugin set it up for me where my app allows it, or give me the exact steps where it does not, so that I do not need to know what an MCP server is.
13. As a student, I want to be told plainly when a tool needs my app restarted, so that I know why this pack does not use it yet.
14. As a student, I want every recommended tool to be free, offline, account-free and the same on Windows, macOS and Linux, so that I never hit a paywall or an OS-specific dead end.
15. As a student, I want a tool never installed for a picture my course does not show, so that nothing lands on my machine for a guess.
16. As the maintainer, I want the Tool list hardcoded in the repo and every entry proven by one sample call in CI, so that no recommendation is ever a dead package.
17. As the maintainer, I want an entry added to the Tool list only when a real course shows that picture, so that I never ship a drawer for a future.
18. As the maintainer, I want Python drawing libraries to be self-installing kinds and everything else recommended, so that "installs itself" is only ever claimed where it is true.
19. As the maintainer, I want no online search for tools, ever, so that the plugin behaves the same in an app with no browsing.

### Form follows the course

20. As a student, I want a ledger in my slides to be a table in my walkthrough, a procedure to be numbered steps, a comparison to be a table and a cause chain to be a flowchart, so that the pack looks like the way my course teaches.
21. As a student, I want prose only where my course uses prose, so that I am not reading paragraphs about something my lecturer drew.
22. As a student, I want every concept to still cover what it should (what it is, why it is so, its formula, a memory tip when one exists), so that the form never loses the content.
23. As the maintainer, I want the Wiki's unit page to record, per topic, the Presentation the course uses and which slide shows it, so that the pack writer and the tools flow both read one section instead of guessing from text.
24. As the maintainer, I want the Presentation recorded by the unit writer that has the slide in front of it, in fixed English kind words, so that the record is language-independent and needs no keyword list.

### The build

25. As a student, I want to send "build the pack for unit 6" and walk away, so that the build never waits on me.
26. As a student, I want a resumed build to write only the missing pages and to rebuild an existing page only when I named it, so that nothing I have is overwritten by accident and nothing is done twice.
27. As a student, I want the pack's graphs drawn and checked by the worker that writes the pack, so that verification is not a separate step I have to ask for.
28. As a student, I want never to be told to install a library by hand, so that a missing tool is the plugin's problem, not mine.
29. As a student, I want one link per recording per section with the times as text, so that the page is readable and the links still open the right minute.
30. As a student, I want a question with no page anchor (a `.doc`, a scan) linked by its file name with where-to-look in words, so that it is still on the Practice page.
31. As a student, I want `coverage.md` to say "analysed" for sources the Wiki has read, including pages read visually and images, so that citing them is honest.
32. As a student, I want the question bank's "solved in a recording" to be true, so that the pack and the question bank never contradict each other.
33. As a student, I want the Short version grouped from the solutions, so that two questions are "the same" only when solving them really takes the same steps.
34. As a student, I want every "Say it" quote to really be in my course's solutions, so that I never learn an invented justification.
35. As a student, I want every symbol and assumption number the pack uses to exist in the unit's notation and assumptions, so that the pack never uses a term my course does not.
36. As a student, I want every drawn graph compared with its slide by a second pair of eyes, so that a label overlapping an axis is caught before I see it.
37. As a student, I want the recordings page's lesson entry to exist before the pack is written, so that the page's link never points at nothing.
38. As the maintainer, I want the workers to read three rule files by path (generic rules, general preferences, course preferences), so that the main context does not carry 25 KB of rules and nothing is pasted twice.
39. As the maintainer, I want `us check` to return the problem list and a summary only, with paragraph bodies behind a flag, so that one unit's check does not cost 98 K characters.
40. As the maintainer, I want the writer and the verifier to read the material independently, so that the verifier verifies rather than agrees.
41. As the maintainer, I want the writer's return in one fixed shape, page list then Known gaps as kind, page, what's missing, so that the main session acts on it without re-reading.
42. As the maintainer, I want every rule that can be checked by code to be a `us check` problem kind and every other rule to stay wording, so that the verifier's judgement is spent only where judgement is needed.

### Self-study and the repo

43. As a self-learner with a folder of material and no university, I want to answer "none" at setup and get the same Course folder, Wiki, Study packs and grounded answers, so that the plugin is not only for students.
44. As a self-learner, I want setup to skip the plugin recommendation and the course-site interview when there is no university, so that I am not asked for a site I do not have.
45. As a self-learner, I want pack wording about "the lecturer" or "the exam" to appear only when my course has those, so that the pages do not talk about things I do not have.
46. As the maintainer, I want the repo to keep its dev hooks, marketplace file and CI public, so that a contributor gets the privacy guard and the tests, and the install command keeps working.
47. As the maintainer, I want every decision above recorded in an ADR where it changes an earlier one, so that the reasoning survives the next time the question comes up.

## Implementation Decisions

### Repo state and order

- Local `main` was five commits behind `origin/main`; it is fast-forwarded. The revert of ticket 23 (`revert-ticket-23`) is rebased on `main` and merged as the first PR. The branch `ticket-23-delete-tool-offer` is not used.
- Six PRs, in this order: (1) graphs only, (2) no subject layer, (3) form follows the course, (4) the build, (5) recommended tools on paper, (6) self-study. Each is independently revertable. One ticket per PR (24 to 29).

### Subject layer (PR 2)

- Deleted: the `economics` plugin (both skills, its plugin manifest, its marketplace entry), the `course_skill` setting and its setup answer and `us setup --course-skill` option, the `us course-skill` command group (`status`, `save`), the generated course-rules file and its path helper, the `subject` kind in plugin recommendations, the README rows and skill table entries, and the CONTEXT.md terms Course skill, Field skill, Subject plugin.
- The study-pack skill's rule resolution becomes three layers, later wins: generic rules, General preferences, Course preferences. Nothing is interviewed.
- Emphasis: the generic rules say the roadmap's "what to know by heart" and the recurring question per topic come from the Wiki course page's exam section and from the past-exam questions in the question bank, never from the student.
- The economics residue moves into the generic rules as conditional advice: when the course explains with models that shift, draw a shift as the original curve, the moved curve and both equilibria, and give each change as a chain (which curve moves, which way, what happens to each variable); when the course has an assumptions sheet, quote assumptions by number; when the course has a formula sheet, everything not on it is "know by heart"; when the course has verbal solutions, the model answer is a chain in the solutions' own words; common mistakes come from the explanations of wrong answers; two units using one name for two concepts get a cross-reference warning in both.
- A course folder whose settings still hold `course_skill` is read as if the key were absent. The README's install section says the economics plugin is no longer needed and can be uninstalled.
- ADR 0011: "Two plugin layers: core and university; per-course rules are the student's preferences file." Supersedes the subject half of ADR 0001 and ticket 02; cites ADR 0002. ADR 0005 is narrowed to the university fallback.

### Pictures (PR 1 and PR 5)

- PR 1 restores the state before ticket 23: `us graph <spec>` from a small spec (ADR 0006), Mermaid for flows, no `us draw`, no `us tools`, no `pictures` module, no `KINDS` registry, no Wiki keyword scan, no offer step in the rules, no `UNISTUDENT_SMOKE` job. ADR 0010 is deleted, not superseded. matplotlib stays available to the graph command the way ADR 0006 states; the graph command's "could not draw" message never tells the student to install anything by hand, and a spec error is reported as a spec error, so the writer fixes the spec and draws again.
- The roadmap's "How to start" ends with one fixed sentence from the generic rules, in the course language: what the plugin draws (graphs and flowcharts) and one example request the student can type in chat, phrased with one of this unit's own concepts.
- PR 5 writes ADR 0012, "Recommended tools come from a tested list and are installed on request", and a "Recommended tools" section of the generic rules, with no code until the Tool list has an entry:
  - **Tool bar.** Free, no account or key, runs offline on Windows, macOS and Linux, installs in one step, driven by a short text spec through an MCP stdio server or a command line, proven by one sample call in CI. Node is allowed in that CI job.
  - **Boundary.** A Python library runnable through `uv run --with` becomes a self-installing kind (a drawer in the repo, no student action, as graphs are). Anything else is a Recommended tool: the agent writes it into the course folder's MCP config where the harness reads a project-level file, or names it with exact steps where it does not. No harness detection code: the agent knows which app it runs in and reads a one-row-per-harness table in the rules (where the config lives, or "name it and give the steps").
  - **Scope.** Course-scoped config first; user-scoped only for harnesses with no project-level file. A newly configured server needs a restart; the pack is built without it and the roadmap says so.
  - **Entry rule.** An entry joins the Tool list only when a real course shows a picture no existing kind draws. The list is hardcoded next to the plugin recommendations. A dispatcher for Python kinds returns at the third real kind, not before.
  - **Evidence.** Two sources, both read by the main session after the pack is written, never a pre-scan by keywords: the unit page's Presentation section (PR 3) and the writer's Known gaps (PR 4), which lists every picture described in words with its kind.
  - **Unattended.** The roadmap's closing line gets, per missing kind with a matching entry, one sentence: what this unit shows and what to say in chat to add it. The writer writes that line from the resolved rules; the main session never asks. `us tools add <name>` is the chat-time command that configures or names the tool and returns the harness steps; it lands with the first entry.
  - Online search for tools is permanently out of scope (ADR 0005's reasoning, and every harness must behave the same).

### Form follows the course (PR 3)

- Generic rules, concepts section: a concept is presented in the form its source uses. A ledger or a two-column comparison is a table; a procedure is numbered steps; a cause chain of three or more steps is a flowchart; a curve is a Graph; prose only when the source is prose. The menu (what it is, why it is so, formula, memory tip) becomes a coverage checklist the concept must satisfy in any form, not a sequence of labelled paragraphs. "Every part earns its place" stays.
- Wiki unit page, new section written by the unit writer: **Presentation**. One line per topic: the form the course uses (fixed English kind words: table, steps, flowchart, graph, circuit, 3D model, and so on, one list in the unit writer's instructions), the slide or page it is on, in the course language otherwise. The unit writer has the slide in front of it, so the record needs no keyword list and works in any language. The study-pack writer opens the recorded page before writing the topic and copies the form.
- The Presentation section is also the evidence source for Recommended tools (PR 5): the kind words are the join key to the Tool list.
- No table-extracting PDF library is added: a form the converter loses is recovered by the writer opening the page, which also covers scans and hand-drawn forms.
- CONTEXT.md gets **Presentation**: the form (table, steps, flowchart, graph, picture kind) a course uses to teach one topic, as recorded on the unit's Wiki page. Avoid: layout, format.

### The build (PR 4)

- **Workers get the tools.** All seven plugin-registered workers' tool allowlists include the UniStudent MCP tools. This is the Claude plugin's grant; in every other harness the worker's instructions are followed by the main agent, which already has them (the conventions block).
- **No questions.** The study-pack skill and the writer never ask during a build. The one interactive flow left is the update flow for an existing pack (propose, the student approves), which the student starts.
- **Resume.** `us study changes --unit N` also lists the pack pages present in the pack folder (`pages_present`). The skill builds the missing pages, rebuilds a page only when the request named it, and says in one line what it skipped. `has_study_pack` stays a state-file fact. Asking for changes no longer creates the Study vault as a side effect.
- **Rules by path.** The skill passes the writer and the verifier three paths: the generic rules file, the general preferences file, the course preferences file. "Paste in full" is deleted. No merged-rules command.
- **Check output.** `us check --labels --json` returns the summary and the problems; paragraph bodies, prefixes and link targets are returned only with a `--full` flag, which the eval grader uses.
- **Links.** One `file:` link per recording per section, with the times as plain text after it; `us check` reads the link from the section for the time entries. A question with no page anchor links the file by its plain name and says where in words.
- **Three new `us check` problem kinds.** (1) `notation`: a Latin symbol or an assumption number used on a pack page that the unit page's Notation or Assumptions sections do not list; Hebrew terms only against the glossary (honest limit). (2) `quote`: a quoted string in a Say it or Model answer block that does not appear in the unit's source pages after whitespace and punctuation normalisation. (3) `return`: the writer's return (saved by the skill next to the pack, in the Hidden folder) is not page list then `Known gaps:` lines of kind, page, what's missing.
- **Verifier.** New step: for every embedded Graph, open the PNG and the slide page its caption cites and report differences in curves, labels, crossings and positions. Reading stays independent of the writer's.
- **coverage.md.** A page written by the source-reader worker records a fingerprint so it is "analysed"; an image with a source page is "analysed"; a recording without a summary stays "pending" (correct).
- **Solved in a recording.** The question-bank stub keeps the field. The unit writer writes it only when a covering recording's TOC exists; the Wiki build marks a unit page stale when a new TOC appears for a recording assigned to that unit or to a lesson whose summary says it covers that unit, so the next build fills it.
- **Short version.** Reading both solutions before grouping is unconditional; the "when unsure" sentence is deleted.
- **Roadmap precondition.** `us study changes` reports covering lessons with no roadmap entry (`lessons_without_roadmap`); the skill runs the Wiki build first when it is non-empty.
- **Known gaps.** The writer's return is the page list, one line per page, then `Known gaps:` with one line per gap as kind, page, what's missing; kinds include `picture` (a picture described in words, with its Presentation kind word). CONTEXT.md gets **Known gaps**: the fixed closing part of a worker's return listing what it could not do, one line per item as kind, page, what's missing. Avoid: notes, warnings.
- **Multi-unit lessons.** Unchanged from the previous round's decision: the recordings page links the lesson's entry and says which other unit the lesson also covers; nothing is pulled into the unit's pack.

### Self-study (PR 6)

- Setup step 1 accepts "none" (plain words: "I'm learning on my own, no university"). It records `university=none`, skips the plugin recommendation and the site interview, and step 5 offers only "my own folder" and "nothing yet". `us plugins recommend` with `none` returns nothing.
- The context file, README template and generic rules make lecturer and exam wording conditional where a sentence would otherwise name something the course does not have: the exam section of the course page is written only when exam information exists; the roadmap's "what the lecturer said" and the recordings page already appear only when recordings exist.
- No rename, no repo split, no change to the product's framing.

### Repo hygiene (no PR)

- Nothing is removed. The marketplace file is the install path, the two hooks are the test runner and the privacy guard, CI backs the README badge. The only personal strings tracked are the public GitHub handle in an install command and a `/Users/me` example path.

## Testing Decisions

- A good test drives behaviour through the `us.py` command line and checks what the student would see (the file written, the JSON returned, the message), never internals. Skill and agent text is tested as text (a sentence present or absent, frontmatter fields, the shared conventions block, no emoji but the warning).
- Seams: the existing two. (1) The command line: `us study changes` fields, `us check` problem kinds and `--full`, `us setup` with `--university none`, `us plugins recommend`, the Wiki build's coverage rows and staleness on a new TOC, `us graph` messages. (2) Skill and agent text through the skill tests. No new seam.
- Per PR:
  - PR 1: the graph tests of the pre-ticket-23 state; a skill test that the picture instructions name the MCP tool before any install request and never tell the student to install by hand; a test that the roadmap rule contains the fixed discovery sentence.
  - PR 2: plugin recommendation tests lose the subject cases; the course-skill fallback tests are deleted; a setup test that a settings file holding `course_skill` is accepted and ignored; a skill test that the study-pack skill names exactly three rule layers; a rules test that the conditional economics advice is present.
  - PR 3: a skill test that the unit writer's instructions contain the Presentation section and its kind words; a rules test for the form-follows-the-source sentence; a Wiki build test that a unit page with a Presentation section survives a rebuild (the generated block does not overwrite it).
  - PR 4: `study changes` on a partial pack returns the present pages and no Study vault is created by asking; `check --labels` without `--full` returns no paragraph bodies; the three problem kinds each on one fixture page (a symbol missing from Notation, a quote absent from the source, a malformed return); coverage rows for a source-reader page and an image with a source page; a unit page marked stale by a new TOC; agent frontmatter tests that every worker lists the UniStudent tools; a skills test that no step in the study-pack skill asks the student during a build.
  - PR 5: a rules test that the Recommended tools section and the harness table exist; the CI job for Tool list entries is a separate workflow that runs when the list changes and does nothing while the list is empty.
  - PR 6: a setup flow test with `--university none` that records it, recommends nothing and writes a context file with no exam section.
- Prior art: `tests/test_simple_study_packs.py`, `tests/test_setup_flow.py`, `tests/test_plugin_recommendations.py`, `tests/test_coverage.py`, `tests/test_wiki_build.py`, `tests/test_citations.py`, `tests/test_graphs.py`, `tests/test_skills.py`, `tests/test_no_emoji.py`.

## Out of Scope

- Online or per-student search for tools, in any harness.
- Pre-building drawers or Tool list entries for majors no real course has shown.
- A product rename, a repo split, or generalising the vocabulary beyond "none" at the university step.
- Removing the dev hooks, the marketplace file or CI from the repo.
- Interview-based per-course rules in any form.
- A table-extracting PDF converter.
- Machine-readable "units covered" for multi-unit lessons (the Wiki-data work deferred earlier).
- A merged-rules command (`us rules`).
- Regenerating the existing course's packs; the owner does that by hand when PR 3 and PR 4 are in.

## Further Notes

- The owner's framing, in order of weight: the plugin must work for every major from the generic rules; pictures and forms must look like the course; a build must never wait on the student; recommendations must be tested before they ship, which rules out anything found online.
- Why the subject layer goes rather than grows: the maintainer cannot test a skill for a major they have not studied, and the measurement showed the existing skills add ten lines over the tuned generic rules. The student-supplied alternative (an interview) fails for a different reason: the student cannot say what to emphasise before learning the unit. The material can, and the Wiki already extracts it.
- Why pictures oscillated: the offer was a permission dialog for an install that already happened without permission, and it was keyed on English words. Both halves of this spec that touch pictures (Presentation as evidence, the roadmap line as the only surface, chat as the install moment) exist so the question cannot come back in the same shape.
- The one honest limit named in this spec: the notation check is reliable for formulas and Latin symbols and weak for Hebrew terms; it checks those only against the glossary.
- Privacy: the repo is public. No course name, course number or personal path goes into code, docs, tests, commit messages or the ADRs. Fixtures are made up.

## Problem Statement

Setup on this branch asks its questions at sixteen different moments spread over hours, so the student has to sit by it from start to finish:

1. **The first minute is a restart.** Step 1 recommends the University plugin and stops setup until the app is reopened, before a single course question is asked.
2. **Recordings are asked about twice, once in the middle of the download.** The OpenU sync asks "which recordings, video or audio" while it downloads; setup step 7 then asks "skip, download or ask per recording" after the download.
3. **Sorting is also asked about twice:** by the sync after its ingest, and again by setup step 6.
4. **Questions wait behind the slow parts.** The exam date and "anything else the course gave you" are asked after the download or the Wiki build, though nothing depends on either.
5. **Transcription is not part of setup at all.** "Ask me per recording" sends the student to `/unistudent:course-recordings` later, which asks again, recording by recording. A course with recordings is never "ready" when the student comes back.
6. **Nothing shows what is about to be downloaded.** A course's recordings can be tens of gigabytes; the student finds out from a full disk, not before.
7. **No one says how long anything takes**, or when to come back.

## Solution

Setup asks everything first, shows a Fetch plan before anything downloads, then runs unattended and calls the student back once at the end.

1. **Questions (about 10 min).** University, course, language, folder, reading app, where the material comes from, anything else the course gave, exam date (optional), and three separate Recording questions, each with what it gives and what it costs, all recommended: transcribe and summarise; frame analysis; keep the video files to watch. Then consent to install speech-to-text and ffmpeg (installed later, in the run). Every install that needs the app restarted (the University plugin, the video-analysis tool) happens together at the end of this block, with one restart.
2. **Before downloading (about 5 to 10 min).** The student logs in to Chrome. The sync scans the course site without downloading. The **Fetch plan** appears: totals by file extension, the free disk space, a rough time estimate, and three choices: download all, skip all recordings, or edit the list (a checklist file, biggest first, everything ticked). Nothing downloads without an explicit OK. Files from site sections that span units get one grouped question: a unit, general, or "I don't know". Then a loud ASCII box: keep the computer on, plugged in and awake, keep the app and Chrome open, about N hours.
3. **Unattended run.** Speech-to-text and ffmpeg install; documents download and the Wiki is built from them (a usable Wiki early); in parallel, recordings download, transcribe in the background, get their summaries and frame analysis, and a final Wiki update follows. Progress messages show a two-line bar (documents, recordings) and the time left. A failure is retried once, then skipped and reported. The run never asks.
4. **Come back (about 5 min).** What is in, what failed and what to do, the "I don't know" files (unsorted, but already in the Wiki), one question about coverage gaps worth fixing, then how to use it and one concrete next step.
5. **Every later sync** shows the Fetch plan before downloading too, or one line when nothing is new.

## Implementation Decisions

### The Fetch plan (Core)

- **Fetch plan** (CONTEXT.md): the list of files a fetch will download, with sizes, that the student approves before anything downloads. Avoid: download list, listing, manifest. The listing stays the internal JSON a University plugin hands to ingest; the Fetch plan is what the student sees and approves.
- The listing gains two optional fields per item: `size` (bytes, when the site gives it without downloading) and `seconds` (a recording's length, when shown). A recording's size is estimated from `seconds` and the documented bitrate and marked estimated.
- A new Core command group, `us fetch-plan`, with three actions:
  - `show <listing>`: writes the checklist file (one ticked line per item, biggest first: size, extension, name, section; "~" on estimates; "size unknown" counted as 0, with a "plus N files of unknown size" line) into the Hidden folder and returns its path, the totals per extension, the grand total, the free disk space (standard library), a fits/does-not-fit flag, the rough time estimate, and the items whose section spans units or names no unit (the sorting module's existing rule).
  - `apply <listing>`: reads the ticks back, writes the approved listing next to it with the student's unit answers as `unit_hint` ("I don't know" leaves the hint absent, so ingest leaves the file unsorted), and records which recordings were approved for transcription with the existing approve step.
  - `status`: from the approved listing, the Manifest and the recordings state, returns documents done/total, recordings downloaded/transcribed/summarised/total, the time left, and the ASCII progress box as text. Plain ASCII, no emoji (the ⚠️-only rule stands).
- Time estimates: download time from a fixed rough network-speed constant; transcription time from the benchmark when one exists, otherwise a fixed rough factor per speech-to-text engine. Every estimate made without a measurement is labelled "rough". `status` replaces the constants with the measured download speed and the benchmark once they exist.
- Own folder: `us import` gains `--dry-run`, returning the file count and total size, for the one-line summary. No Fetch plan for a folder already on the disk.

### The OpenU sync (University plugin)

- The sync splits into scan, plan, download. Scan: the file list (as now) plus each file's size from a request that does not download the body, falling back to "size unknown"; the recordings' titles and lengths only, no stream links. Plan: `us fetch-plan show`, the three choices, `apply` after an explicit OK. Download: documents in the course tab as now; the stream links collected only after the OK, recording by recording, just before each download; an expired link is re-collected once, then the recording is skipped and reported.
- The sync's own recordings question goes. It reads the Recording choices from the course's Settings (recording level, frame analysis, keep video) and asks only when the course has none recorded (a sync run outside setup on an older course).
- The sync's post-ingest sorting question goes when it runs inside setup: setup asked before the download. Outside setup it stays, with the "I don't know" answer added.
- Every sync shows its Fetch plan; when the scan finds nothing new, one line: "Nothing new on the site since <date>".
- The generated-fallback path builds the same listing by following its saved notes, so it reaches the same `us fetch-plan show`.

### Course setup

- Stages (`us setup-progress`) become: `university`, `course`, `language`, `path`, `format`, `material`, `recordings`, `installs`, `plan`, `run`, `capabilities`. The old `fetch`, `sort` and `analyze` stages map onto the new ones for a setup started on an older version (the existing renamed-stages map). The overview's step count equals the numbered steps.
- **Block 1, questions:** the overview says "about 10 minutes of questions, then you can leave for a few hours". University (the "none" answer and the fallback interview as now; the plugin recommendation is recorded, not installed yet), course, language, folder, reading app, where the material comes from (site, own folder, both, nothing yet; own folder: which folder, official or added, and the `--dry-run` line), anything else the course gave, exam date (optional, stored as an answer and applied once the Course folder exists). Then three Recording questions, each its own question with what it gives, its cost per hour of recording, and "recommended": transcribe and summarise (recording level 3, approved in the Fetch plan, not per recording later), frame analysis (says it uses a lot of Claude usage), keep the video files to watch (a new Settings field, `keep_video`). Then consent to the speech-to-text and ffmpeg installs. `us setup` runs at the end of the block, so the Course folder exists before any install writes into it.
- **Restart, at most once:** the University plugin and the video-analysis tool (when frame analysis is on) are installed together, the video tool through the Recommended-tool path of ADR 0012 (course folder config where the harness reads one, otherwise exact steps). One "close and reopen the app, then run setup again" message. No restart needed: go straight on.
- **Block 2, before downloading:** login, scan, the Fetch plan with its three choices and the chat loop (each change shows the updated plan; only an explicit OK applies it), then the grouped unit question with "I don't know", then the box from `us fetch-plan status` before the run starts. The box's warning text is fixed: keep the computer on, plugged in and awake, keep this app and Chrome open, about N hours. Setup changes no power settings.
- **Recording files:** a recording is always downloaded (setup sets `recording_level` 3 with transcription, else 1), so one not transcribed now can be transcribed later with `course-recordings`. When frame analysis is off and `keep_video` is false, the recording is fetched audio-only. When frame analysis is on and `keep_video` is false, the video is kept until its analysis is done, then replaced by an audio-only copy. A kept file is always there for the time links (see Further Notes).
- **The run, in this order and never asking:** installs (speech-to-text, ffmpeg); documents download and ingest, then the course Wiki build on them (the `course-wiki` steps, workers in parallel where the app has them); in parallel, recordings download and transcribe in the background (the existing background job), then each transcript's summary (and frame analysis when on), the Recorded-lessons judgement as in `course-recordings` step 5 (a recording it cannot judge stays where the site put it and is named in the report), and a final Wiki build, unit writers and check. Between steps, a progress message with the `status` box. A failure: one retry, then skip and add it to the report. Resume: running setup again reads the `run` stage and repeats the idempotent steps (ingest skips files already in, transcription skips transcribed recordings, the Wiki build is incremental).
- **Come back:** the report (in, failed with what to do, unsorted-but-in-the-Wiki files), the coverage summary and one question about gaps worth fixing (as step 8 does now), then step 9 unchanged.
- `course-recordings` stays for recordings added later; inside setup its per-recording question is replaced by the Fetch plan's approval.
- **ADR 0013:** "Setup asks everything first, approves downloads with a Fetch plan, then runs unattended." Records why setup transcribes without asking per recording (the Fetch plan with real numbers is the approval), why all restarts are batched, and why the sync never asks during a download.

## Testing Decisions

- Same seams as above: the `us.py` command line, and skill and agent text through the skill tests. No new seam. A good test feeds a made-up listing and checks the checklist file, the JSON and the box text the student would see, never internals.
- `us fetch-plan show`: a listing with documents, recordings with `seconds`, and one item without a size returns totals per extension, "~" on recording lines, the unknown-size line, biggest-first order, a does-not-fit flag when the total exceeds a stubbed free space, and the multi-unit items.
- `us fetch-plan apply`: unticked lines are absent from the approved listing; a unit answer becomes `unit_hint`; "I don't know" leaves it absent and the ingested file lands in unsorted with a Wiki source page; approved recordings are recorded as approved for transcription.
- `us fetch-plan status`: counts and the box text from a fixture state; "rough" in the text before a benchmark, not after.
- `us import --dry-run`: count and size, nothing copied.
- `us setup-progress`: the new stages in order; an old `fetch`/`sort`/`analyze` progress file resumes at the matching new stage.
- Settings: `keep_video` is stored and read; a fetch with frame analysis off and `keep_video` false runs audio-only.
- Skill text: setup asks every question before the `plan` stage and none in the `run` stage; the three Recording questions are separate; the box text is fixed; the OpenU sync has no recordings question when Settings hold the choices, collects stream links only after the OK, and shows the Fetch plan on every sync.
- Prior art: `tests/test_setup_flow.py`, `tests/test_setup_progress.py`, `tests/test_site_ingest.py`, `tests/test_recording_streams.py`, `tests/test_recordings.py`, `tests/test_skills.py`, `tests/test_no_emoji.py`.

## Out of Scope

- Low-quality video downloads (recorded in `docs/TODO.md` for a later discussion).
- Detecting the Claude plan's usage limit, or changing the computer's power settings.
- Emoji in setup messages: ASCII art, bold and uppercase only.
- A live-updating progress bar: each progress message prints a new box.
- Per-recording transcription questions inside setup.
- A table or HTML editor for the Fetch plan: the checklist is a plain Markdown file.

## Further Notes

- **Assumption to confirm with the owner:** "keep the video files = no" keeps an audio-only copy instead of deleting the recording, because every summary, roadmap and announcement links to a minute in the recording file (CLAUDE.md point 4). Deleting it would break those links. If the owner wants the file gone entirely, the time links need another target, which is a separate decision.
- Unverified on the live site: whether a file's size can be read without downloading it, and whether recording lengths always show. Both have a fallback ("size unknown"), so neither blocks the design.
- The documented 1.8 Mbit/s works out to about 0.81 GB per hour (the site notes' "3 GB per 3 hours" is about 2.4 GB); estimates use the bitrate.

# Spec: UniStudent v2 — dynamic onboarding and generated fallbacks

> Layout sections superseded by ADR 0007 (three visible folders, hidden Wiki, no Raw).

Status: grilled with Noam, ready to ticket · Created 2026-09-30 · Owner: Noam
Extends `docs/spec/v1.md` — read that first. This doc only covers what's new or changed; v1's per-course folder layout, grounding rule, and plugin-layering ADRs are unchanged.

## Problem Statement

v1 ships full support for exactly one university (OpenU) and one subject (economics/macro), each hand-authored ahead of time. A student anywhere else, or in any other course, gets nothing today: no fetcher, no course-specific study-pack rules, and — since `course-setup` is the only entry point and doesn't ask "which university" as its own step — no guided way in at all beyond installing the right plugin themselves.

Setup also assumes it runs start-to-finish in one sitting. A slow fetch or analyze step that gets interrupted (or that the student deliberately stops because it's taking a while) currently has no resume path other than starting over.

Recording analysis is also, today, silently more expensive than it needs to be: `recording-summarizer` calls into `mcp-video-analyzer` per segment (`get_frame_at`/`analyze_moment`) whenever that MCP server happens to be installed, with no separate opt-in, no shown cost, and no gate tied to the recording level the student actually chose. This is also a spec/implementation mismatch: v1 explicitly deferred frame-based analysis to "video level 2" and marked it out of scope, but the code already does it opportunistically.

## Solution

Give every student — not just OpenU/economics ones — a working setup, additively, on top of what v1 already ships:

1. A university-selection stage runs before course selection. It checks for an installed, hand-authored plugin first (using its fetcher/MCP/API/scripts as-is when one exists) and only falls back further when none does.
2. When no plugin exists, the student is interviewed once (site URL, how they organize/prioritize material) and the plugin generates a persistent fallback reference file from that interview — never re-researched live in later sessions. The same generate-once-fallback pattern applies one level down, for course-specific study-pack rules, when no subject/course skill exists either.
3. Setup becomes staged and resumable: it writes down which stage it's on, so stopping and coming back picks up where it left off instead of restarting.
4. Setup ends with a plain-language explanation — spoken in the conversation, not just left in a README — of how the student feeds the plugin more material later, and how they make sure a brand-new AI session (in any app) is actually working from this course's wiki.
5. Visual frame analysis of recordings becomes an explicit, separately-costed opt-in, never bundled silently into whatever the student already chose for transcription.

## User Stories (new/changed since v1)

Numbering is independent of v1; treat as v2-only.

### University & course discovery
- As a student at a university with no plugin, I want the plugin to ask for my university's site URL and how I organize/prioritize material, and generate a working fallback from that interview, so that I'm not blocked on someone hand-writing a plugin for my school first.
- As a student, I want the plugin to always check first whether a plugin for my university is already installed, and use its actual API/MCP/scripts when it has them, so that a generated fallback is only ever a last resort.
- As a student in a course with no subject/course skill, I want the same interview-and-generate fallback for course-specific study-pack rules (what to emphasize, how to summarize), so that every course gets a working pack even before it's specifically supported.
- As the maintainer, I want a generated fallback to be a normal, inspectable file (a new reference/skill file), not a black box or an in-memory decision, so that it can be reviewed, corrected, upgraded to a hand-authored plugin later, or reused by the next student at that university.
- As the maintainer, I want the university axis and the subject axis to stay independent (per ADR 0001) — a generated university fallback never carries study-pack rules, and vice versa.

### Setup flow
- As a student, I want one guided flow: pick my university, pick my course, pick a local path, pick a format, fetch/organize material, then analyze it — in that order, each a distinct stage.
- As a student, I want to be asked for more material before the fetch stage is considered done ("any other books, solutions, anything else the course gave you? the more you give, the better this works"), so the plugin doesn't start analyzing on an incomplete set.
- As a student, I want to be told, briefly, why converting my PDFs/videos into an LLM-readable wiki is worth the wait (it's what lets the AI answer only from my course, cite its source, and catch when general knowledge conflicts with how my course teaches it) before the analyze stage starts, so I understand what I'm waiting for.
- As a student, I want setup to record which stage it's on to disk as it goes, so that if I stop it (it's slow) and come back later, it picks up exactly where it left off instead of restarting.
- As a student, I want setup to close by demonstrating value, not just listing commands: it should proactively suggest a first concrete thing to try (e.g. "want a video roadmap for unit 1, or a summary of what's covered so far?").
- As a student, I want to be able to trigger a deeper interview at any stage of setup (not just the university/course fallback stages) when the default questions don't fit my situation.

### Post-setup guidance
- As a (non-technical) student, I want setup to end by explaining, in plain language, how I add more material later (drop it in the inbox, run add) and how I make sure a brand-new AI session — in any app — is actually using my course's wiki (open it in this folder; here's the one-line prompt to paste if it isn't auto-read), so that the wiki doesn't go stale or get silently ignored.

### Token-friendly recordings
- As a student, I want visual frame analysis (mcp-video-analyzer per-segment slide identification) to be its own explicit, opt-in choice with a shown cost estimate, never bundled silently into "level 3", so that I know when I'm paying extra tokens for it and can skip it.
- As a student, I want the transcript-only path (no frames) to remain the default even when mcp-video-analyzer is installed, so that adding the tool doesn't silently change my token spend.

## Implementation Decisions

### University/course fallback generation
- Priority order per axis (university, then course/subject): (1) an installed, hand-authored plugin for this exact university/course — use its fetcher/MCP/API/scripts as-is; (2) a previously generated fallback for this exact university/course — reuse as-is; (3) generate one now via an interview + confirm, write it to disk, use it. Never re-research live once (2) exists.
- The interview for a generated university fallback asks: the site URL, and how the student organizes/prioritizes material (what's worth keeping vs. skipping) — mirroring what a human maintainer would have asked before hand-writing `openu`'s `site.md` (ticket 01's process, generalized). Findings are shown to the student before being trusted (confirm-before-persist).
- Generated fallbacks live in a new local (not repo-published) location, e.g. `~/.unistudent/generated/<university-slug>/site.md` and `.../<subject-slug>/<course-slug>.md`, following the same file shapes as `plugins/openu/skills/openu-sync/references/site.md` and `plugins/economics/skills/macro/SKILL.md` respectively, so a maintainer can later promote a good one into a real plugin with minimal changes.
- Per ADR 0001, university and subject axes never merge: a generated university fallback only ever contains site-access/sorting knowledge, never study-pack rules, and vice versa. There is no override chain within the university axis itself (a course has exactly one university; nothing to override).
- Future extensibility (no work now): a university's installed plugin may eventually wrap a real MCP server or API instead of browser-driven scraping instructions; the fallback-generation interview and the "check installed plugin first" priority order already accommodate that without change.

### Setup: staged and resumable
- Stages, in order: (0) university [skipped once a plugin or generated fallback is resolved], (1) course, (2) local path, (3) format, (4) fetch & organize [ask for more material before leaving this stage; prompt about videos here], (5) analyze [explain the wait and the "why LLM wiki, not raw PDFs/videos" pitch], (6) show capabilities & suggest a first concrete action.
- Progress is written to disk (a small state file next to the course's hidden settings) after every stage completes: the last completed stage, and any answers already given. Re-running setup (or `course-help`, if it detects incomplete setup) reads this file and resumes at the next unfinished stage rather than re-asking earlier ones.
- Long-running stages that can be interrupted mid-stage, not just between stages, should checkpoint at whatever finer grain the underlying operation already supports (sync is already manifest-driven/resumable per v1; recording jobs already checkpoint per-file) — setup's own stage file only needs to know "stage 4 in progress" vs. "stage 4 done", not duplicate that finer resumability.
- A short, explicit "why this takes time / why an LLM wiki beats raw files" explanation is shown once per course, right before stage 5 starts, in 2-3 plain sentences, not left to documentation.
- A deeper, `/grill`-style interview is available as an explicit escape hatch at any stage, for when the default question set doesn't fit (an unusual site structure, an unusual course format).

### Token-friendly recordings
- Split what "level 3" currently bundles: transcript + written summary/TOC (text-only, cheap) stays the default heavy option. Per-segment visual frame analysis via `mcp-video-analyzer` becomes a separate, explicit opt-in on top of level 3, shown with its own cost estimate (segments × one vision call each) before the student agrees to it. Not choosing it means `recording-summarizer` never calls `get_frame_at`/`analyze_moment`, regardless of whether the MCP server happens to be installed.
- This closes the current implementation/spec mismatch: v1's "Out of Scope (v1)" already deferred frame-based analysis to v2 ("video level 2"), but `recording-summarizer.md` today invokes it opportunistically whenever the tool is present, with no level gate and no cost shown.

## Testing Decisions (additions to v1)

- Seam (new): generated-fallback interview — given a synthetic site URL and a scripted student Q&A, check the resulting reference file matches the expected shape. Same fixture-based style as existing seams, not a live network/model eval.
- Seam (new): setup resume — start setup, stop after each stage in turn, restart, assert it resumes at the correct next stage with prior answers intact.
- The existing grounding eval (seam 3) is unaffected; no new eval is needed for university/course fallback content itself (it's reference material, not graded output).

## Out of Scope (v2, deferred further)

- A dedicated tutor skill (interactive Q&A / practice mode). Explicitly deferred — `study-pack` remains the only summary/study output for now; no generic tutor skill exists yet.
- Real per-university MCP servers/APIs. Noted as a future extension point the design already accommodates, not built now.
- Promoting a generated fallback into a real, repo-published plugin. A manual maintainer step for later, not automated.

## Further Notes

- Reference for the interview-and-generate pattern's UX discipline (staged, confirmed, one focused question at a time, visible progress): `mattpocock-skills:wizard`'s process, adapted to a live conversational flow rather than a standalone script the student runs alone — the wizard skill targets steps outside the AI's control (a third-party dashboard); this flow is the AI doing the work itself, so only the staging/confirmation discipline transfers, not the bash-script mechanism.
- See `docs/adr/0005-generated-fallbacks-are-cached-not-live.md` for why fallback generation is interview-once-then-cache rather than live per-session research.

## Suggested tickets (in order)

1. **University-selection stage + plugin/fallback priority check.** Add a stage before `course-setup`'s existing course step: detect installed university plugins, detect a previously generated fallback, or fall through to interview-and-generate. Blocked by: nothing (can start immediately).
2. **Generated-fallback file format + interview flow**, for both university and course/subject axes, writing to `~/.unistudent/generated/...`. Blocked by: 1.
3. **Setup stage-state file + resume logic** in `cli.py`/`course-setup` SKILL.md. Blocked by: nothing, can be done in parallel with 1-2.
4. **Split recording level 3's frame analysis into an explicit opt-in** with a shown cost estimate, in `course-recordings` SKILL.md and `recording-summarizer.md`. Blocked by: nothing, independent of the rest.
5. **Post-setup plain-language explanation step**: how to add material later, how to point a new session at the wiki (including the non-rooted-session paste-in fallback). Blocked by: nothing, can land any time; cheapest ticket here.
6. **README updates** reflecting the new onboarding order and the reconnect-a-session paragraph. Blocked by: 1, 5.

# The OpenU sync can log in by itself, from a Saved login, through a site client in the core

The OpenU sync used to reach the course site only through the student's own logged-in Chrome (Claude in Chrome): every scan and download was a script run in the site's tab, and the AI was told never to ask for or type the password. A student without Claude in Chrome got no sync, and one with it had to log in again whenever the session ran out. Now a student can keep a Saved login, and the core's `us openu` command logs in, scans and downloads with plain HTTP, with no browser. Chrome stays as the path for a student without a Saved login, or when it stops working.

The Saved login is a plain JSON file in the student's UniStudent home folder (`logins.json`, readable only by them), never in the course folder, which may sit in a cloud-synced folder. The student types it into a one-time form that `us openu login` serves on their own computer (127.0.0.1), not into the chat, so the AI never sees the password: an AI that has seen it can be tricked by text in a course file into repeating it, and AI assistants refuse to type a person's password for them. The form logs in once before it saves, so a typo is caught while the student is there. We chose a plain file over the OS password store because the student asked for it and it needs no extra library on any OS. The cost is that any program running as the student can read it, as it can their browser profile. The skills tell the AI never to open the file.

The site client lives in the core (`openu.py`), against the rule that site access belongs to the University plugin (ADR 0011), because the core is the only part with a Python runtime that every app reaches through the MCP server. A second MCP server in the OpenU plugin would duplicate it, and loading the plugin's code from a path at run time would let the two drift apart. The OpenU plugin keeps the sync skill and the site notes. A second university with a site client would get its own module the same way.

Everything the Chrome scripts did works over HTTP (checked 2026-11-21): the files list, folders, the section pages that link the video collections, and the recordings. A recording's length, date, attachments and player token come from the collection's `actions.php` (`getplaylist`), and the player's stream link from the CDN's redirector, which needs no cookies. Scheduled syncs, with no chat open, are left for later.

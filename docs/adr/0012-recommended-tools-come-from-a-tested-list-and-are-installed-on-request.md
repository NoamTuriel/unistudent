# Recommended tools come from a tested list and are installed on request

When a unit shows a kind of picture UniStudent cannot draw, the only source of a tool for it is the Tool list: a hardcoded list next to the plugin recommendations, each entry proven by one sample call in a CI job of its own. An entry clears the tool bar: free, no account or key, offline on Windows, macOS and Linux, one-step install, driven by a short text spec through an MCP stdio server or a command line. The boundary decides who installs it: a Python library runnable through `uv run --with` is a self-installing kind with a drawer in the repo, as graphs are (ADR 0006); anything else is a Recommended tool, written into the course folder's MCP config where the app reads a project-level file, or named with exact steps where it does not. The agent knows which app it runs in and reads a one-row-per-app table in the generic rules; there is no harness detection code.

An entry joins only when a real course shows a picture no existing kind draws, and a dispatcher for Python kinds returns at the third real kind, not before. This is ticket 23's revert note taken as a rule: three of its four kinds were speculative, never checked against a course, and left a dispatcher built for four around one real entry. The evidence is what the course itself records, read after the pack is written: the unit page's Presentation kind words and the writer's Known gaps `picture` lines, never a keyword scan (ticket 23's English keywords matched nothing in a Hebrew Wiki).

The unattended surface is one roadmap sentence per missing kind with an entry: what this unit shows and what to say in chat to add it. Nothing is asked during a build and nothing is installed for a guess. The install happens in chat on the student's request, through `us tools add <name>`, which writes the course-scoped config or returns the steps and says when a restart is needed; a newly configured server is not used by the pack already built. That command and the CI runner land with the first entry; until then the list is empty and the CI job does nothing.

We chose a tested, hardcoded list over an online search for the same reason ADR 0005 caches fallbacks instead of looking them up live: most supported apps cannot browse, an unverified find can be a dead package, and every app must behave the same.
